# Продукт и границы первой версии

Статус: проектирование. Документ фиксирует согласованные требования,
а не утверждает, что они уже реализованы.

## Продукт

Онлайн-покер с выбором стола из списка. Автоматического подбора игроков нет.
В первой версии поддерживается только No-Limit Texas Hold’em.
Чат игроков и наблюдателей не входит в MVP.
Тестовые protobuf-контракты не являются утверждённым API продукта;
сохранять совместимость с экспериментальным Game API не требуется.

## Аккаунты и доступ к продукту

- Регистрация выполняется по email, паролю, уникальному никнейму
  и отдельному отображаемому имени.
- Все игровые функции доступны только после регистрации и входа:
  просмотр списка столов, просмотр конкретного стола, создание и участие.
- Ссылка или код приглашения не обходят обязательный вход в аккаунт.
- Гостевой доступ не поддерживается в MVP.
- Регистрация и вход доступны без существующей авторизованной сессии.

- В MVP подтверждение email и восстановление пароля отсутствуют;
  эти возможности отложены на следующие этапы.

У пользователя есть уникальный никнейм и отдельное отображаемое имя,
которое может повторяться. Уникальность никнейма учитывает регистр:
`Player` и `player` — разные никнеймы. Постоянный идентификатор пользователя — `user_id`;
игровые данные связываются с ним, а не с никнеймом.
- `username`: от 3 до 24 символов; разрешены латинские буквы, цифры и `_`.
  Регистр учитывается. Изменение никнейма в MVP не поддерживается.
- `display_name`: от 1 до 40 символов после удаления пробелов по краям;
  кириллица разрешена. Пользователь может менять отображаемое имя.

### Вход и сессии

- Вход выполняется по email и паролю; никнейм не используется для входа.
- После успешной регистрации пользователь сразу авторизован.
- Авторизация на нескольких устройствах разрешена, но игра или наблюдение
  доступны только в одном активном окне по правилам блокировки.
- «Выйти» завершает текущую сессию аккаунта.
- «Выйти на всех устройствах» завершает все сессии аккаунта.
- Сессия аккаунта и допуск активного игрового окна — разные сущности.

Формат токенов, сроки действия, механизм отзыва и влияние выхода
на уже открытое игровое соединение будут определены при проектировании API.

## Доступ к столам

Владелец выбирает один из трёх режимов:

| Режим | Общий список | Условие входа |
| --- | --- | --- |
| Публичный | Видим | Без пароля |
| С паролем | Видим, отмечен как защищённый | Пароль |
| По приглашению | Скрыт | Ссылка или код приглашения |

Пароль и секрет приглашения не публикуются в общем списке.
### Приглашение в скрытый стол

- На стол действует одно многоразовое приглашение: ссылка и соответствующий код.
- Приглашение действует до закрытия стола или отзыва владельцем.
- Владелец может заменить приглашение; предыдущее перестаёт работать.
- Замена приглашения не выгоняет уже вошедших участников и наблюдателей.
- Любой авторизованный пользователь с действующим приглашением может войти
  за стол, в том числе как наблюдатель.
- Приглашение не резервирует игровое место.
- Отзыв или замена запрещают новые входы по старому приглашению;
  восстановление действующего участия после обрыва связи не считается новым входом.

Правила видимости карт наблюдателей описаны ниже.

## Каталог столов

- Владелец задаёт название стола; названия могут повторяться.
- Список показывает название, владельца, число занятых и общее число мест,
  блайнды, стартовый стек, наличие пароля и состояние игры.
- Поддерживается поиск по названию.
- Фильтры MVP: есть свободные места, без пароля, игра ещё не началась.
- По умолчанию новые столы показываются первыми.
- Скрытые столы не попадают в общий список и поиск.
- Для просмотра каталога необходима авторизация.

Пагинация, правила поиска по регистру и допустимая длина названия
будут определены в контракте API.

## Формат сессии

MVP: постоянный стол. Игроки могут приходить и уходить между раздачами.
Во время раздачи можно занять свободное место; новый игрок участвует
со следующей раздачи. Новые раздачи продолжаются, пока хватает игроков.

Будущий режим: закрытая партия. Состав участников фиксируется при запуске,
новые игроки после запуска не допускаются. Детальные правила этого режима
не входят в текущую версию API.

## Вход, посадка и готовность

- После входа за стол пользователь сначала становится наблюдателем.
- Для участия пользователь сам выбирает свободное место.
- После посадки пользователь явно подтверждает готовность кнопкой «Готов».
- Создатель стола проходит тот же путь; роль владельца не занимает место автоматически.
- Создание и просмотр стола не начисляют стартовый стек и не занимают место.
- При первой успешной посадке выдаётся стартовый стек; для повторной посадки
  применяются правила повторного входа конкретного стола.
- Пользователь, занявший место во время раздачи, может участвовать
  только со следующей раздачи после подтверждения готовности.

- Готовность сохраняется между раздачами: повторно нажимать «Готов»
  перед каждой раздачей не требуется.
- Команда «Пропускать раздачи» во время участия в раздаче ставит sit-out
  в ожидание: он включается после завершения текущей раздачи и не сбрасывает руку.
- Между раздачами добровольный sit-out включается сразу.
- Для возвращения игрок нажимает «Готов» и участвует со следующей раздачи.
- Пять минут до освобождения места отсчитываются с фактического начала sit-out,
  а не с момента запроса отложенного sit-out.

## Параметры игры

| Параметр | Согласованное правило |
| --- | --- |
| Число мест | От 2 до 9, выбирает владелец |
| Блайнды | Малый и большой задаёт владелец; автоматического роста нет |
| Первая раздача | Запускается владельцем при наличии минимум двух готовых игроков |
| Следующие раздачи | Автоматически после короткой паузы, пока хватает игроков |
| Изменение правил | Только до начала первой раздачи |
| После первой раздачи | Правила фиксируются на всё время существования стола |

Пауза между раздачами — 5 секунд, фиксированная для MVP.
После паузы новая раздача начинается только при наличии достаточного
числа готовых игроков с положительным стеком.

### Значения по умолчанию

| Настройка | Значение |
| --- | --- |
| Доступ | Публичный |
| Количество мест | 6 |
| Стартовый стек | 1 000 |
| Малый / большой блайнд | 5 / 10 |
| Время хода | 30 секунд |
| Повторный вход | Сохранить предыдущий стек |
| Повторная выдача | По запросу игрока, без одобрения владельца |
| Лимит повторных выдач | 3 на игрока за всё время существования стола |

Владелец может изменить эти настройки до начала первой раздачи.
Пауза между раздачами не является настраиваемым параметром MVP.

## Таймер хода и отключение игрока

- Владелец выбирает время хода: 15, 30 или 60 секунд. По умолчанию — 30 секунд.
- При истечении времени выполняется check, если он доступен; иначе — fold.
- Потеря соединения не останавливает раздачу и не сбрасывает таймер.
- После таймаута игрок переходит в sit-out: пропускает следующие раздачи,
  его стек сохраняется. Это не отменяет его права на банк текущей раздачи.
- После возвращения игрок подтверждает готовность и участвует со следующей раздачи.
- Переподключение само по себе не считается новым входом и не начисляет фишки.

## Явный выход во время раздачи

- Явный выход игрока во время незавершённой раздачи означает fold:
  его карты сбрасываются, внесённые ставки остаются в банке,
  права на выигрыш в этой раздаче он лишается.
- Исключение: если игрок уже находится в all-in, его рука доигрывается
  автоматически. Выход не лишает его права на выигрыш в доступных ему банках.
- Явный выход отличается от обрыва связи: при обрыве действуют правила
  таймера хода и переподключения.

- После явного выхода место окончательно освобождается по завершении раздачи.
- До завершения этой раздачи игрок не может заново сесть за этот или другой стол.
- Итоговый стек вышедшего игрока сохраняется, включая результат доигранного all-in.
  При возвращении применяются настройки повторного входа конкретного стола.
- Выход и повторный вход не создают второй стек во время незавершённой раздачи.

## Освобождение места при неактивности

- После 5 минут непрерывного sit-out игрок освобождает место и становится
  наблюдателем. Для отключённого пользователя это не создаёт соединение:
  при возвращении он восстанавливает доступ уже без занятого места.
- Если игрок ещё участвует в текущей раздаче, освобождение места
  откладывается до её завершения.
- Стек сохраняется для повторного входа согласно настройкам стола.
- После освобождения места отключённый пользователь не удерживает стол
  от удаления как пустого.

Наблюдатели не удерживают пустой стол от закрытия.
Срок хранения стека после освобождения места пока не согласован.

## Одно активное окно и один стол

- У пользователя может быть только один активный стол: либо участие в игре,
  либо наблюдение. Одновременное наблюдение за другим столом запрещено.
- Для игры и наблюдения допускается только одно активное окно пользователя.
- Второе окно блокируется: оно не получает игровые события и не может
  отправлять игровые действия. Принудительного переноса управления нет.
- Блокировка должна обеспечиваться сервером, а не только интерфейсом.
- Блокировка окна не означает выход со стола и не изменяет стек игрока.

- Активное окно регулярно подтверждает соединение.
- Если подтверждений нет 30 секунд, блокировка освобождается.
- После освобождения блокировки пользователь может подключиться заново;
  место и стек сохраняются согласно правилам стола.
- Освобождение блокировки не останавливает и не сбрасывает таймер хода.
- Старое соединение после утраты блокировки не должно получать игровые
  события или отправлять действия, даже если связь восстановилась.

Технический механизм подтверждения соединения и восстановления после
перезагрузки страницы будет определён при проектировании транспорта.

## Наблюдатели и видимость карт

- Авторизованный пользователь может наблюдать за столом, не занимая игровое место.
- Для наблюдения за защищённым столом требуется пароль или приглашение
  согласно режиму доступа стола.
- Наблюдатели видят общие карты, ставки, банк и стеки игроков.
- Нераскрытые карманные карты не передаются наблюдателям через API или события.
- На showdown наблюдателям доступны только фактически раскрытые карты.
  Сброшенные и остальные нераскрытые карты остаются скрытыми.

Возможность владельца запрещать наблюдение и ограничения числа зрителей
ещё не согласованы.

## Владелец и закрытие стола

- Владелец может передать свою роль другому участнику.
- При явном выходе владельца роль получает оставшийся участник,
  который раньше остальных присоединился к столу.
- Потеря соединения сама по себе не передаёт роль владельца.
- Пустой стол удаляется через 10 минут.
- Команда владельца «Закрыть стол» запрещает новые входы.
  Текущая раздача доигрывается, после чего стол закрывается.
  Если раздача не идёт, стол закрывается сразу.

- Стол считается пустым, когда нет игроков, занимающих места.
- Наблюдатели и владелец без занятого места не останавливают таймер закрытия.
- Для нового стола десятиминутный отсчёт начинается с создания.
- Посадка игрока отменяет таймер; после освобождения последнего места
  начинается новый десятиминутный отсчёт.
- После десяти минут без занятых мест стол закрывается;
  подключённые наблюдатели получают уведомление.
- Место, удерживаемое до завершения раздачи после выхода или sit-out,
  остаётся занятым до фактического освобождения.
- Закрытие стола не удаляет доступную игрокам историю раздач.

## Восстановление после сбоя Game-сервиса

- В MVP незавершённая раздача после падения или перезапуска Game-сервиса
  отменяется, а не продолжается.
- Стеки восстанавливаются до значений перед началом отменённой раздачи,
  до списания блайндов и других обязательных ставок.
- Стол и участники восстанавливаются из сохранённых данных.
- Результаты уже надёжно зафиксированных завершённых раздач не откатываются.
- Для этого требуется надёжное хранение состояния между раздачами
  и исходных стеков до начала каждой раздачи.

Порядок возобновления игры после восстановления и обработка изменений
состава участников во время отменённой раздачи ещё предстоит согласовать.

## История раздач и архив

- Пользователь может просматривать историю только тех раздач, в которых
  участвовал как игрок: действия, ставки, участников и результаты.
- Владение столом не даёт дополнительных прав на чужую историю или скрытые карты.
- Наблюдатели видят текущую игру и её результаты, но не получают права
  на архив раздач стола на основании наблюдения.
- История остаётся доступной участнику после закрытия стола.
- Игрок видит свои карты и публично раскрытые карты соперников.
  Чужие нераскрытые карты недоступны через историю.
- Текущие и недавние раздачи обслуживает Game.
- Для старых данных выделяется отдельный сервис Archive.
- Завершённые и отменённые раздачи подлежат переносу в Archive через 24 часа
  после завершения или отмены. Перенос выполняется в фоне;
  при недоступности Archive он откладывается без остановки игры.
- Game удаляет свою копию только после подтверждённого сохранения в Archive.
- Повторная передача раздачи с тем же `hand_id` не создаёт дубликат.
- Клиент получает историю через единый API Gateway независимо от места хранения.

В MVP архивная история хранится без автоматического удаления.
24 часа — порог переноса в Archive, а не срок хранения истории.
Политика очистки может быть добавлена на следующих этапах.

## Малый и нулевой стек

- Игрок с положительным стеком может участвовать в раздаче, даже если стек
  меньше большого блайнда.
- Если средств недостаточно для обязательной ставки, игрок вносит доступную
  сумму и оказывается в all-in; права на банки рассчитываются по внесённым суммам.
- Игрок с нулевым стеком не допускается в новую раздачу и находится в sit-out.
- Повторная выдача фишек выполняется только по отдельному запросу игрока
  и согласно настройкам стола. Автоматического пополнения нет.
- Во время sit-out из-за нулевого стека действует общий пятиминутный таймер
  освобождения места.

## Экономика: этапы

### Этап 1 — фишки внутри стола (MVP)

Новый участник получает установленный для стола стартовый стек.
Баланс аккаунта не используется. Стартовые условия одинаковые,
но после раздач стеки могут различаться.

Правила повторного входа и выдачи фишек задаются настройками стола.

Согласованные правила повторной выдачи:

- Только при нулевом стеке и между раздачами.
- Выдача восстанавливает стек до стартового размера.
- Владелец выбирает режим: запрещена, по запросу игрока или с одобрением владельца.
- Владелец может задать лимит повторных выдач одному пользователю
  за всё время существования стола.
- Первый стартовый стек не является повторной выдачей.
- Выход, повторный вход и переподключение не сбрасывают счётчик выдач.
- Если настройка повторного входа предусматривает восстановление стартового
  стека, оно также подчиняется общим условиям выдачи, разрешению и лимиту.
  Повторный вход не позволяет обойти требование нулевого стека.
- Автоматического пополнения нет: требуется запрос игрока.
- Переподключение восстанавливает прежнее участие и само по себе не начисляет фишки.

Срок хранения стека вышедшего игрока,
обработка ожидающего одобрения запроса при выходе и возврат к готовности
после выдачи ещё предстоит определить.

### Этап 2 — бесплатная валюта аккаунта

При регистрации начисляется бесплатная игровая валюта.
Появляются баланс аккаунта, внесение средств за стол и возврат остатка.
Для балансов и операций выделяется отдельный сервис Wallet.
Размеры начислений и правила операций ещё предстоит согласовать.

### Этап 3 — покупаемая валюта

Добавляется отдельная валюта, которую можно купить за деньги.
Платежи не входят в MVP. Возможность обмена, передачи и вывода средств,
а также использование этой валюты в игре пока не определены.

## Открытые решения

- Возобновление после сбоя и изменения состава во время отменённой раздачи.

- Механизм подтверждения активного окна и восстановление после перезагрузки страницы.

- Технический механизм сессий, отзыв доступа и выход при активной игре.
- Настройки доступа зрителей и ограничения их числа.
- Пагинация списка столов и правила поиска по названию.
- Ограничения числовых параметров настроек стола.
- Границы сервисов, владение данными, HTTP/gRPC API и доставка событий клиенту.

## Порядок проектирования

1. Согласовать пользовательское поведение и граничные случаи.
2. Определить ответственность сервисов и владельцев данных.
3. Описать основные сценарии и отказы.
4. Зафиксировать общие правила API и архитектурные решения.
5. Описать HTTP API в OpenAPI и внутренние контракты в protobuf.
