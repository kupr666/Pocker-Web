# Архитектура

Статус: проектирование. Состав сервисов MVP согласован; технические
механизмы взаимодействия ниже являются предложением до детализации API.
Продуктовые требования: [product.md](product.md).

## Сервисы и ответственность

| Сервис | Ответственность |
| --- | --- |
| Gateway | Внешний HTTP API, соединение для игровых событий, проверка авторизации, преобразование запросов в gRPC |
| Auth | Email для входа, хеш пароля, токены, сессии и состояние учётной записи |
| User | Профиль: user_id, уникальный никнейм, отображаемое имя, дата создания; позже — аватар и настройки пользователя |
| Lobby | Создание и настройки столов, список, пароли и приглашения, владелец, допуск игроков и зрителей |
| Game | Места, готовность, раздачи, карты, ставки, стеки, таймеры, sit-out и персональные игровые события |
| Archive | Долговременная история завершённых и отменённых раздач, поиск истории игрока; принимает данные от Game через 24 часа |
| Wallet (после MVP) | Балансы аккаунтов, начисления, внесение средств за стол и возврат остатка |

Auth и User связываются общим неизменяемым `user_id`.
Пароли и сессии не входят в публичный профиль User.
Никнейм уникален с учётом регистра: `Player` и `player` — разные никнеймы.
Отображаемое имя может повторяться. API не должен автоматически приводить
никнейм к нижнему регистру; проверка уникальности в хранилище должна
соответствовать этому правилу.

- `username`: 3–24 символа, латинские буквы, цифры и `_`;
  изменение в MVP не поддерживается.
- `display_name`: 1–40 символов после удаления пробелов по краям,
  допускает кириллицу и изменение пользователем.

## Согласованная модель авторизации

- Auth принимает email и пароль для входа.
- После успешной регистрации пользователь получает авторизованную сессию.
- Сессии аккаунта могут существовать на нескольких устройствах.
- Поддерживаются завершение текущей сессии и завершение всех сессий аккаунта.
- Ограничение одного активного игрового окна действует независимо от числа
  сессий аккаунта. Игровой допуск необходимо связывать с действующей сессией.

Формат токенов, сроки действия, механизм отзыва и прекращение активных
соединений при выходе пока требуют технического решения.

## Предлагаемые границы данных

Каждый сервис изменяет только данные, которыми владеет. Другие сервисы
обращаются через контракт, а не напрямую к его таблицам.

Lobby разрешает доступ к столу; Game управляет участием и игрой.
Для списка Lobby получает сведения о занятых местах от Game.
Окончательное решение о возможности занять место принимает Game.
Способ обновления списка и допустимая задержка ещё не выбраны.

Централизованную блокировку активного окна и стола предлагается разместить
в Lobby. Gateway и Game должны учитывать актуальность допуска.
Конкретный механизм аренды, её продления и отзыва требует отдельного решения.

## Предлагаемый сценарий регистрации

1. Gateway передаёт регистрационные данные в Auth.
2. Auth создаёт учётную запись и инициирует создание профиля в User.
3. Успех регистрации возвращается после готовности учётной записи и профиля.

Этот сценарий пока не является готовым контрактом. До реализации нужно
определить состояния незавершённой регистрации, уникальность email и никнейма,
идемпотентность, восстановление после частичного сбоя и выдачу токенов.
Распределённая атомарная транзакция между Auth и User не предполагается автоматически.

## Восстановление Game в MVP

Согласован упрощённый вариант: после сбоя незавершённая раздача отменяется,
стеки восстанавливаются до её начала. Стол и участники восстанавливаются
из сохранённых данных. Полное восстановление хода незавершённой раздачи
не входит в MVP.

Требования к дальнейшему проектированию хранения:

- До начала раздачи надёжно сохранить её идентификатор и исходные стеки
  до списания блайндов.
- Итоговые стеки и признак завершения раздачи фиксировать атомарно.
- Отмену и восстановление сделать идемпотентными: повторный запуск
  восстановления не должен повторно начислять фишки.
- Разделять сохранённое участие за столом и состояние конкретной раздачи,
  чтобы восстановление не теряло новые входы и не возвращало вышедших игроков.
- Определить момент подтверждения завершения раздачи клиентам относительно
  фиксации результата, а также защиту от двух одновременно активных обработчиков стола.

Конкретное хранилище и схема транзакций пока не выбраны.

## История и Archive

Archive — отдельный сервис в составе проектируемой первой версии.
Game хранит недавние раздачи; через 24 часа после завершения или отмены
они переносятся в Archive. Внешний API истории остаётся единым в Gateway.

Требования к переносу:

- Передавать только окончательно зафиксированные завершённые или отменённые раздачи.
- Идентифицировать раздачу по `hand_id`; повторный запрос не создаёт дубликатов.
- Считать сохранение успешным только после надёжной записи на стороне Archive.
- Удалять копию в Game только после подтверждения сохранения.
- При сбое Archive сохранять данные в Game и повторять перенос позже.
- Во время пересечения копий выдавать одну раздачу, без дубликатов.
- Не выбирать источник истории только по возрасту: перенос может задержаться.
- Применять проверку доступа и фильтрацию скрытых карт независимо от источника.
- Разрешать чтение истории только участникам соответствующей раздачи;
  статус владельца стола или наблюдателя не даёт дополнительных прав.
- Сохранять данные об участии в истории самой раздачи, чтобы закрытие стола
  или выход из него не лишали игрока доступа к своей истории.

Архивная история в MVP хранится без автоматического удаления.
Транспорт фонового переноса, механизм повторов и единая пагинация между
хранилищами ещё не определены.
Сам по себе выбор Archive не требует отдельного брокера сообщений.

## Следующие решения

- Формат токенов, сроки действия, отзыв сессий и остановка активных соединений.
- Внешние HTTP-маршруты и gRPC-методы сервисов.
- Доставка игровых событий и восстановление после потери соединения.
- Хранилище Game, границы транзакций и возобновление игры после отмены раздачи.
- Жизненный цикл стола на границе Lobby и Game.
- Ошибки API, идемпотентность и проверка полномочий внутренних вызовов.
